# troubleshoot — 不具合報告からのスキル改善と PR 作成

`maintain` は「改善しよう」という能動的な依頼を扱う。このスキルは逆に、**実運用中に何かがおかしかった**
という受動的な報告を起点にする。原因切り分けとチェックリストは `maintain` に従い、
このスキル固有の責務は「証拠の確認」と「専用ブランチでの PR 作成」。

<HARD-GATE>
実行可否をユーザーに確認する前に、診断・修正・PR 作成へ進むことを禁止する。
誤動作を検知した／報告されただけで自動的に走り出さない。スキップが選ばれたら何もせず終える。
ただし依頼文が既に着手を明示している場合（「直して」「PR にして」）は確認済みとみなし、
手順0では**スコープ（対象スキル・対象リポジトリ）の確認だけ**を行って進んでよい。
参照ファイルを読むのは準備であって診断ではない——ゲート前に読んでよい。
</HARD-GATE>

## 前提

- 開始前に `.claude/skills/maintain/SKILL.md` を読む。契約表と「変更の種類別チェックリスト」（A〜D）がここでの正
- 「スキルを改善して」のような能動的・網羅的な改善依頼は `maintain`（+ 必要なら `sdd-improver` エージェント）に譲る。
  こちらは「動かしてみたら想定外だった」という具体的な1件の事象が起点
- **プロダクト実装への指摘は `receive-review`、スキル自体の挙動の異常が `troubleshoot`**
  （「PR レビュー対応がうまくいかなかった」= receive-review スキルの挙動が問題ならこちら）

## 手順

0. **実行可否とスコープの確認**: 上の HARD-GATE に従い「troubleshoot を実行するか、スキップするか」を問う。
   このとき**対象スキル名・対象リポジトリ（配布コピーか正本か。手順6の同定を前倒しする）・
   これから行うこと（診断→修正案の提示→承認後に PR）**を添える。診断結果はまだ不要
1. **事象の確認（証拠必須）**: 何をしたか・期待した挙動・実際の挙動・関連スキル名/フェーズ/該当する
   state.md やレポートの箇所を確認する。再現できる具体例なしに次へ進まない
   （`maintain` の失敗パターン「ループの空転」＝証拠なしの「たぶんこう直すと良い」を踏襲しない）。
   着手前に `docs/maintain-log.md` に同一事象の `[不具合却下]` 行がないか確認する（あれば再診断しない）
2. **原因切り分け**: 該当スキルの SKILL.md と `maintain` の契約表を突き合わせ、単一スキルの欠陥か
   スキル間境界の契約違反かを判定する。境界の契約違反が疑われる場合は `sdd-improver`（監査モード・
   報告のみ・対象事象を指定）に切り分けを委譲してよい（自己審査を避ける）。
   **派遣は general-purpose に `.claude/agents/sdd-improver.md` のパスを渡して Read で従わせる**
   （`subagent_type: sdd-improver` はプロジェクト外から解決されずエラーになる）。
   委譲先が今回の事象と因果関係のない指摘を返したら、それは PR に混ぜず `maintain` 送りとして報告に列挙する
3. **修正案の作成**: `maintain`「変更の種類別チェックリスト」（A〜D）に従う。契約表のどれかに触れるなら
   「追随が必要な場所」を同一変更に含める（1ファイルだけ直すのは最頻の欠陥源）
4. **ユーザーに提示・承認**: 診断結果・修正差分・触れるファイル一覧を提示し、適用してよいか確認する。
   無断で適用や PR 作成に進まない。手順4と6の承認はまとめてよい（差分と PR 方針を同時に提示する）が、
   **手順0のゲートだけは独立させる**——診断のコストを払う前の意思確認だから
5. **適用と検証**: 承認後に変更を適用し、`maintain`「変更後の必須検証（コミット前）」の全項目に従う。
   **実行主体の線引き**: 機械的検証（`scripts/validate`・旧記述の grep・発火シミュレーション）は自分で行う。
   「この修正で再発が防げるか」という判断を伴う評価は、契約表に触れる変更なら `sdd-improver` に出す
   （maintain の「自己審査は必ず別のサブエージェントに出す」はこちらに掛かる）
6. **ブランチ〜PR**:
   - **修正対象リポジトリの同定**（手順0で確認済みならそれに従う）。スキルセットはコピー配布されるため、
     配布物のコピー上で PR を作っても上流に届かない。判定材料は `git remote -v`（remote 不在はコピーを疑う）・
     `git worktree list`・`.git` がファイルなら worktree。判断がつかなければ正本のパスをユーザーに確認する
   - **`fix/skill-<対象スキル名>-<短い説明>` を main（既定ブランチ）から分岐する**。不具合報告は
     SDD 実行中の `feature/*` ブランチ上で起きるのが典型で、そこから切ると未完成の機能差分が PR に混入する
   - **worktree 運用中は現ディレクトリで切り替えない**——main は別ディレクトリがチェックアウト済みで
     `git checkout main` が失敗する。main 側のディレクトリで作業し、進行中 worktree は温存する
   - 未コミットの作業があれば、元ブランチでコミットするか stash することをユーザーに確認してから移動する。
     **完了後は元のブランチ（worktree なら元のディレクトリ）に必ず戻す**
   - コミット後、push と `gh pr create --base main` の前に必ずユーザーへ最終確認を挟む。
     PR 本文は「事象（証拠）→ 原因 → 修正内容 → 検証結果（validate OK）」の順で書く
   - `gh` が使えない（未認証・remote なし）場合は、ブランチにコミットするところまでで止め、
     PR 作成手順をユーザーに提示して終える
7. **却下時の記録**: 診断の結果スキル側の欠陥ではないと判断した場合は修正せず、
   `docs/maintain-log.md` に `[不具合却下]` を付けて1行追記する（書式の正は `maintain`。
   ファイルが無ければ新規作成する）

## 原則

- **1件 = 報告された事象1つ**（修正箇所1つではない）。その事象を塞ぐのに必要な追随は、
  複数ファイルにまたがってもすべて同一 PR に含める（塞ぎ残した経路があれば再発するため）。
  事象と因果関係のない指摘は PR に混ぜず `maintain` へ回す
- `specs/*/state.md` は更新しない（進行中の SDD の状態とは独立に動く割り込みスキル）
