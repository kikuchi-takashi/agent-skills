## 摩擦ログ

### 【効いた】
- **verify:前提チェック** — 現在フェーズ verify ＋ review 承認で通過判定でき、前周の「全ルートで自分を却下する」欠陥は解消を実測
- **verify:手順1「ユニットテストの再実行で代用しない」** — 6/6 緑の裏で AC-2 の終了コード 0 を直接実行で検出。代用なら虚偽完了だった
- **verify:手順3「修正 diff を review を素通りさせない」** — 直接実装（implement なら省略可）だったが、タスクレビューを通した
- **verify:手順6「承認前に『完了』と書かない」** — 全件 PASS 直後に停止できた。「完了」は承認後の別コミット（`d76ff5b`）
- **sdd:差し戻し「verify FAIL の差し戻しは順行を繰り返さない」** — review 再承認へ回り道せず verify に直接戻した
- **verify:手順1「一時ファイルはプロジェクト外に」** — `mktemp -d` で `git add -A` 混入なし
- **implementer-prompt:TDD** — RED を先に見て、既存テストが終了コード未検証だった事実が明確化
- **receive-review:HARD-GATE／手順1** — spec に根拠のない `--shout` を追従実装せず「不当・誤解」に分類し反証を用意
- **receive-review:手順1 表「妥当（実装品質）vs（仕様変更）」** — AC-2 が出力先を規定していないと確認し、不要な AC 修正（救済ルート）を回避
- **receive-review:手順3 ／ sdd:バイパス節「例外は receive-review 経由」** — 新規フォルダを作りかけて既存フォルダ追加に即修正。相互参照が効いた
- **sdd:state.md フォーマット「ルート欄は据え置き」** — ルート欄を「バイパス」に書き換える誤りを防いだ

### 【迷った】
- **verify:手順3「単体呼び出し時は呼び出し側」** — 呼び出し側＝ユーザーか自セッションか読めない。自セッションが sdd 規則で書くと解釈
- **verify:手順3 ／ sdd:差し戻し** — 修正ループ中の implement に「フェーズ完了承認」（implement:フェーズ完了）が要るか不明。不要と解釈し止まらず進めた
- **verify:手順3** — FAIL 検出時に一度ユーザーに報告して止まるか、修正ループを回し切るか不明。承認要件が書かれていないため回し切った
- **sdd:state.md フォーマット** — 修正ループ／再オープンの追加タスクの行名（T-n 続番か「修正n」か）。A は「修正1」、B は「T2」と**表記が割れた**
- **review:手順5** — 2行 diff のタスクレビューに最安モデルで「実装者以外の目」が担保できるか判断が割れる
- **receive-review:手順1〜3 の承認タイミング** — 分類提示で一度止まるか、再オープン＋spec-lite 作成まで進めて1回で取るか不明。再オープン（state.md 編集）をユーザー確認前に行ってよいかに時間を要した
- **receive-review:手順2「戻し先フェーズ」** — バイパスで直す場合 specify か implement か。sdd バイパス節まで辿らないと決まらない
- **receive-review:手順1** — 質問形の指摘（「漏れではないですか？」）が「不当・誤解」と「不明瞭」のどちらか。分類表に「新機能要望（スコープ外）」の扱いが無い

### 【矛盾】
- **implement:タスクごとの実行方式「直接実装はタスクレビューを省略できる」 vs verify:手順3・sdd:差し戻し「修正 diff を素通りさせない」** — 修正ループの直接実装で後者が優先と読めるが、implement 側にバイパス以外の例外（修正ループ）が書かれていない
- **implement:前提チェック「state.md に『ルート: バイパス』の記録あり」／verify:前提チェック「フルルートは…バイパスは…」 vs sdd:フォーマット節・receive-review:手順2「ルート欄は書き換えない」** — 再オープンのバイパスサイクルでは判定キー（ルート欄）が「フル」のまま。verify は旧 review 承認で偽陽性、implement は tasks.md 要求に読める

### 【不足】
- **sdd:起動手順6 ／ verify:手順6 ／ receive-review:手順2〜3** — sdd が動いていない経路（verify 単体・receive-review 経由）での**承認行の記録主体**が未定義。A は「verify 承認」行、B は「specify 承認」行を自分で書いた。sdd 手順6 の例外は「現在フェーズ→完了の更新のみ」であり承認行に触れない。auto 手順2 は auto が承認行を書くと明示しているが手動側に対応物がない
- **sdd:バイパス節「バイパス採用と理由を state.md に記録する」** — どの欄・どの行書式か未定義（B は承認履歴の specify 承認行に理由を詰めた）
- **verify:手順3** — 修正コミットの粒度・state.md のコミットタイミング（差し戻し直後か verify 復帰後か）
- **verify:手順3** — 本体が直接修正する場合の BASE 記録・TDD 証拠の要否が verify から辿れない（implement→implementer-prompt を自力で読み合わせた）
- **verify:手順1** — 「Then を実証する」の粒度（stderr/stdout 分離・ファイル不在の事前確認）は自己判断
- **verify:手順5** — 軽微指摘が採用された場合の修正ルート（修正ループ？新規バイパス？）
- **receive-review:手順1** — 検証で過去成果物（plan の準拠表・review-report）の判定誤りが判明した場合の扱い（訂正か記録か）
- **receive-review:手順2** — 再オープン時の「修正ループ: N/10」をリセットするか継続するか
- **receive-review:手順4** — PR 返信文を出すタイミング（分類直後の下書きか完了時のみか）

### 【過剰】
- **verify:禁止フレーズ表** — HARD-GATE と手順3「N/M PASS と正直に書く」で足り、判断に影響しなかった
- **verify:手順7 worktree 後始末** — 単一ディレクトリ運用では読んでも判断に関与しない
- **receive-review:手順2「複数指摘はまとめて1回」** — 今回は1件のみ有効で影響なし（複数妥当のケースでは効くため削除不適）
- **sdd:SKILL.md の起動時手順・合理化の罠・フェーズ表** — receive-review から参照されない節は今回読んでも判断が変わらず。節単位の参照指定で十分

## 前周修正の判定

- verify 前提チェック: A（フル）・B（再オープン→バイパス）の両経路で verify 自身を却下せず通過 → **前周の修正は機能**
- 手順6「承認前に『完了』と書かない」: A・B とも全件 PASS で停止し、A は承認後の別コミットで「完了」 → **機能**
- sdd 差し戻し節「直接 verify に戻す」: A・B とも review 再承認を挟まず遷移 → **機能**
- 修正ループ行: A で 1/10 に更新 → **機能**（B は差し戻しなしのため 0/10 のまま）
- 残る穴: ①sdd 不在経路（verify 単体・receive-review）の**承認行の記録主体**が未定義で操縦者が自分で書いた ②再オープン後の verify 前提チェックが**旧サイクルの review 承認で偽陽性**になり得る
