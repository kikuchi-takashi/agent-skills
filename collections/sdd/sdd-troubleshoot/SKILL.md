# sdd-troubleshoot — 不具合報告からのスキル改善と PR 作成

`sdd-maintain` は「改善しよう」という能動的な依頼を扱う。このスキルは逆に、**実運用中に何かがおかしかった**
という受動的な報告を起点にする。このスキル固有の責務は「証拠の確認」と「専用ブランチでの PR 作成」——
判断の材料（契約表・チェックリスト等）は `sdd-maintain` に集約されているので、下記「前提」でまとめて参照する。

<HARD-GATE>
ゲートは3点——**①実行可否（手順0）②修正の適用（手順4）③push/PR（手順6）**。
それぞれ個別に確認する。**前段の承認は後段を兼ねない**（「実行して」は「適用してよい」ではない）。
誤動作を検知した／報告されただけで自動的に走り出さない。スキップが選ばれたら何もせず終える。
ファイルを読む事実確認はゲート前に行ってよい。判定・修正・PR はゲート後。
依頼文が着手を明示している場合（「直して」「PR にして」）は①を満たしたとみなしてよいが、②③は残る。
</HARD-GATE>

## 前提

- 開始前に `sdd-maintain` スキルを読む。以下は同ファイル内の節で、下記手順から
  「sdd-maintain の」を都度付けずに節名だけで参照する: 契約表／変更の種類別チェックリスト（A〜D）／
  変更後の必須検証（コミット前）／失敗パターン／改善ループの回し方（`sdd-improver` の派遣方法）
- 「スキルを改善して」のような能動的・網羅的な改善依頼は `sdd-maintain`（+ 必要なら `sdd-improver` エージェント）に譲る。
  こちらは「動かしてみたら想定外だった」という具体的な1件の事象が起点
- **プロダクト実装への指摘は `sdd-receive-review`、スキル自体の挙動の異常が `sdd-troubleshoot`**
  （「PR レビュー対応がうまくいかなかった」= sdd-receive-review スキルの挙動が問題ならこちら）

## 手順

0. **実行可否とスコープの確認**: HARD-GATE の例外（依頼文が着手を明示）に該当しなければ
   「実行するか、スキップするか」を問う。該当すればスコープの確認だけを行って進む。
   いずれも**対象スキル名・対象リポジトリ（配布コピーか正本か。手順6の同定を前倒しする）・
   これから行うこと（診断→修正案の提示→承認後に PR）**を添える。診断結果はまだ不要。
   このとき `gh`・remote の有無も確認し、**PR を作れない環境なら先に伝える**——「PR にして」という
   依頼の前提が崩れていることを、手順6まで進んでから告げない
1. **事象の確認（証拠必須）**: 何をしたか・期待した挙動・実際の挙動・関連スキル名/フェーズ/該当する
   state.md やレポートの箇所を確認する。再現できる具体例なしに次へ進まない
   （失敗パターン「ループの空転」＝証拠なしの「たぶんこう直すと良い」を踏襲しない）。
   着手前に `docs/maintain-log.md` に同一事象の `[不具合却下]` 行がないか確認する（あれば再診断しない）
2. **原因切り分け**: 該当スキルの SKILL.md と契約表を突き合わせ、次の3択で判定する——
   ①単一スキルの欠陥 ②スキル間境界の契約違反 ③**スキルは記述どおり動いた**（ユーザー入力不足・誤用・環境要因）。
   **③の判定が先**: 「SKILL.md のどの記述に反したか」を引用できなければスキルの欠陥ではない → 手順7へ。
   ②が疑われる場合は `sdd-improver`（監査モード・報告のみ・対象事象を指定）に、改善ループの回し方に
   従って委譲してよい（自己審査を避ける）。
   委譲先が今回の事象と因果関係のない指摘を返したら、それは PR に混ぜず `sdd-maintain` 送りとして報告に列挙する
3. **修正案の作成**: 変更の種類別チェックリスト（A〜D）に従う。契約表のどれかに触れるなら
   「追随が必要な場所」を同一変更に含める（1ファイルだけ直すのは最頻の欠陥源）
4. **ユーザーに提示・承認**: 診断結果・修正差分・触れるファイル一覧に加え、
   **却下（スキルの欠陥ではない）の可能性をどう棄却したか**を1〜2行添えて、適用してよいか確認する。
   差分は3ファイル程度までなら全文、それ以上なら要点＋ファイル一覧に落とす。
   手順0で「実行して」と言われたことは適用の承認ではない——ここで改めて止まる
5. **適用と検証**: 承認後に変更を適用し、変更後の必須検証（コミット前）の全項目に従う。
   **実行主体の線引き**: 機械的検証（`scripts/validate`・旧記述の grep・発火シミュレーション）は自分で行う。
   「この修正で再発が防げるか」という判断を伴う評価は、契約表に触れる変更なら `sdd-improver`
   （監査モード・報告のみ・対象事象を指定）に出す
   （失敗パターン「自己審査」＝独立した評価担当が利用できなければ現在のセッションで監査し、その制約を報告、はこちらに掛かる）
6. **ブランチ〜PR**:
   - **修正対象リポジトリの同定**（手順0で確認済みならそれに従う）。スキルセットはコピー配布されるため、
     配布物のコピー上で PR を作っても上流に届かない。判定材料は `git remote -v`（remote 不在はコピーを疑う）・
     `docs/genesis/` の有無・`.git` がファイルなら worktree（＝正本の一部）。
     判断がつかなければ正本のパスをユーザーに確認する
   - **`git switch -c fix/skill-<対象スキル名>-<短い説明> main` ——起点 `main` を必ず明示する**。
     不具合報告は SDD 実行中の `feature/*` 上で起きるのが典型で、起点を省くと feature の先端から分岐し
     未完成の機能差分が PR に混入する。**worktree 内でもこの形なら成功する**（`git checkout main` は
     別ディレクトリがチェックアウト済みで失敗するが、起点指定の `switch -c` は通る。進行中 worktree は温存）
   - 未コミットの作業があれば、元ブランチでコミットするか stash することをユーザーに確認してから移動する。
     **完了後は元のブランチ（worktree なら元のディレクトリ）に必ず戻す**
   - コミット後、push と `gh pr create --base main` の前に必ずユーザーへ最終確認を挟む。
     PR 本文は「事象（証拠）→ 原因 → 修正内容 → 検証結果（validate OK）」の順で書く
   - `gh` が使えない（未認証・remote なし）場合は、ブランチにコミットするところまでで止め、
     PR 作成手順を提示して終える。**remote 自体が無いなら remote 追加→push→PR の順で提示する**
7. **記録**（どちらの結末でも `docs/maintain-log.md` に1行残す。書式の正は `sdd-maintain`。無ければ新規作成）:
   手順2で③と判定したら修正せず `[不具合却下]` を追記して終える。修正した場合は `[不具合修正]`
   （日付・対象スキル・事象要約・ブランチ名）を追記し、③を棄却した理由を PR 本文の「原因」に含める——
   このスキルは `state.md` を持たないので、判断の証跡は PR とログにしか残らない

## 原則

- **1件 = 報告された事象1つ**（修正箇所1つではない）。その事象を塞ぐのに必要な追随は、
  複数ファイルにまたがってもすべて同一 PR に含める（塞ぎ残した経路があれば再発するため）。
  事象と因果関係のない指摘は PR に混ぜず `sdd-maintain` へ回す
- `specs/*/state.md` は更新しない（進行中の SDD の状態とは独立に動く割り込みスキル）
