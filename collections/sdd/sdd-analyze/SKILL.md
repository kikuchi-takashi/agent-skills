# sdd-analyze — 整合性検証（read-only）

<HARD-GATE>
このスキルは成果物を書き換えない。報告のみ。修正は該当フェーズへの差し戻しで行う。
</HARD-GATE>

## 前提チェック

tasks.md が承認済み（state.md の承認履歴に記録あり）でなければ、sdd に差し戻す。
plan.md・spec.md も承認済みであることを合わせて確認する——どれか1つでも未承認なら、
下流の tasks.md が古い前提の上に組まれている可能性があるため、そのフェーズへ差し戻す。

## 検証項目（すべて実施）

1. **カバレッジ表**: 全 AC-n × タスクの対応表を作る。どのタスクにも現れない AC は「漏れ」
2. **spec↔plan 矛盾**: sdd-plan のコンポーネント・データモデルが spec の受け入れ基準と食い違っていないか
3. **constitution 違反**: plan・tasks が sdd-constitution の各項目に反していないか（sdd-plan の準拠チェック節の検算）
4. **検証コマンドの実行可能性**: tasks.md の各検証コマンドが現環境で実行できる形式か。ツールの存在は実際に確認する（`which` やバージョン表示を実行する。推測しない）。存在しないツールは重大（実行不能）として報告する
5. **タスク間インターフェース**: あるタスクが使う関数・型を、依存先タスクの完了条件が定義しているか（名前・シグネチャの不一致は実装時に必ず衝突する）

## 検出例（各カテゴリ1つ）

- 漏れ: AC-4「空入力で再入力を促す」がどのタスクの完了条件にもない
- 矛盾: spec は「保存は即時反映」、sdd-plan のデータモデルは「終了時に一括書き出し」
- constitution 違反: 「依存追加は最小限」に対し、sdd-plan が標準ライブラリで書ける処理に外部ライブラリを選定
- 実行不能: 検証コマンドが `npm test` だがプロジェクトに package.json がない
- インターフェース不一致: T3 が `save(task)` を呼ぶ前提だが、T1 の完了条件は `save(task_list)` を定義

## 重大度の較正

- **重大** = 実装に入ると手戻りが確実なもの（AC 漏れ・spec↔plan 矛盾・インターフェース不一致・実行不能な検証コマンド）
- **軽微** = 実装中に吸収できるもの（表記ゆれ・冗長な記述・粒度の不揃い）
- 迷ったら「これを放置して実装した場合、どのフェーズまで戻るか」で判定する。tasks 内で直る＝軽微、spec まで戻る＝重大
- **sdd-review（重大/重要/軽微の3値）との対応**: analyze は実装前チェックのため2値で足りる（迷ったら重大側に倒す）。
  sdd-analyze の軽微＝sdd-review の軽微相当。sdd-analyze の重大は sdd-review の重大・重要のどちらにもなりうる——
  実装後に取り返しがつくかで review 側が改めて判定する
- 判定の第一基準は**テスト可能な挙動への影響**。文言の精度だけの問題（挙動は変わらない）は軽微とし、指摘には残す

## 報告フォーマット（提示に加え specs/YYYY-MM-DD-機能名/analyze-report.md にも保存する）

```markdown
## 整合性レポート
### カバレッジ表
| AC | タスク | 状態 |
### 問題（重大度順）
- [重大|軽微] <内容> → 差し戻し先: <フェーズ>
### 判定: 実装に進んでよい | 差し戻しを推奨
```

会話への提示だけでなくファイルにも保存する（state.md が壊れた場合の復旧材料になる。sdd の「state.md が壊れている・矛盾している場合」参照）。
重大問題ゼロでも必ずレポート全文を提示し、ユーザーの確認を得てから sdd-implement へ進める（承認記録は sdd の責務）。
「問題なし」の1行報告は禁止——カバレッジ表と確認した項目を示すこと。何を見てゼロと言ったかが分からない報告は検証ではない。

## 差し戻し規則

重大が1件でもあれば差し戻しを推奨し、修正後は**必ず再度 sdd-analyze を実行する**（修正が新しい矛盾・漏れを
持ち込むことは珍しくない。review・verify も同じ規則）。差し戻し先が spec/plan/tasks のいずれであっても、
sdd の通常の順行フロー（差し戻し先→…→analyze）を経由すれば自然に再実行されるが、
analyze は単体でも呼び出し可能なため、単体運用時は呼び出し側が明示的に再実行の要否を判断すること。
