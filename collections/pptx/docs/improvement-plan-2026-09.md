# 改善案 — OSS調査を踏まえた残りの3件（2026-09-06）

デザイン系OSSを調査し、**使えるライブラリの範囲**（python-pptx / lxml / Pillow / XlsxWriter / 標準ライブラリ。追加導入も実行時ネットワークも無し）で成立するものだけを選んだ。3件は実装済み（コントラスト検査 / 視覚QAの定型 / 見た目の基準画像、`9f0ec93`）。ここに残りを、着手できる形で書く。

## 調査で分かった前提の訂正

**先の分析で「siril9 は2,183件から抽出したスタイル辞書を持つ」と書いたが、これは取り下げる。** `large_style_corpus_catalog.json` の `policy.allowed_record_types` に `"inferred style descriptors from names, paths, query route, and extension"` とあり、実体はGitHub検索でヒットした**リポジトリ名とパスからの推定**である。実レコードを数えると、`bold-startup-narrative` に分類された635件の `layout_tags` と `palette_tokens` は**全件が完全に同一**だった。`frequency: 635` は「635種類のデザインの証拠」ではなく「635件がこのバケットに入った」件数にすぎない。

つまり**語彙の量で負けてはいない。** 我々に無いのは量ではなく、**組み合わせを作る仕組み**である（下の案2）。

同様に、siril9 の `forbidden_moves` は `qa_gate.py` からも `layout_lint.py` からも参照されておらず、検査されているのは「非空の文字列リストか」という**形だけ**である。**構造化されたデータの形をした散文**であり、機構ではない。真似るなら検査は自作する前提になる。

## 案1: デッキの文法を宣言し、**実際に検査する**

### 何が無いか

ページ単位の原型は20種あるが、**デッキ全体として何の様式なのかを宣言する層が無い**。そのため「この種の資料でやってはいけない手」を書く場所が無い。`instruction.md` が営業向けにストーリーラインの型を5つ持っているのは、この層を用途側で肩代わりしている状態である。

### 形（`pptx-design` の成果物に足す）

`design-lock.json` に `grammar` を足す。**新しいファイルを増やさない**——ロックは既に4スキルの受け渡し物になっており、検査（`--lock`）の経路も通っている。

```json
"grammar": {
  "id": "answer-led",
  "reading_path": ["結論", "証拠", "含意と担当"],
  "arc": ["結論", "文脈", "証拠", "трейドオフ", "行動"],
  "invariant": ["各展示物に含意を1行付ける", "最後は担当と期日で終える"],
  "forbidden": ["結論を最終ページまで遅らせない", "証拠の代わりにカードを並べない"]
}
```

フィールドの切り方は siril9 の `taste_grammar_catalog.py` に倣う（`narrative_arc` / `reading_path` / `invariant_moves` / `forbidden_moves`）。**8種を輸入しない**——粒度の根拠がデータで示されておらず、同梱の実例デッキ2件でも使われていなかった。まず `answer-led`（結論先出し）と `evidence-led`（問い→方法→結果→限界）の2つだけ置き、足りなければ増やす。

### 検査（ここが本体）

`forbidden` を散文で終わらせない。**書ける検査だけを書く**というのが線引きになる。

| 禁じ手 | 検査できるか | 検査の仕方 |
|---|---|---|
| 結論を最終ページまで遅らせない | できる | `arc` の先頭が `結論` なら、本文の最初の3枚に `closing` か `hero-number` か `statement` が現れることを見る |
| 証拠の代わりにカードを並べない | できる | 既存の `CARD_ROW` と `EQUAL_EMPHASIS` を、そのデッキの `forbidden` に該当するとき **軽微→重要** に上げる |
| 各展示物に含意を1行付ける | できない | 「含意かどうか」は文意の判断。目視観点に回す |

**検査できないものは `forbidden` に書かない。** 書いてよいのは、`GRAMMAR_VIOLATION` として lint が実際に出せるものだけにする。書けないものは `visual-qa-prompt.md` の観点に足す。これで siril9 の「形だけ検査」を繰り返さずに済む。

### 見積り

`pptx-design` に節を1つ、`pptx_lint.py` に `GRAMMAR_VIOLATION` を1コード、`review-rubric.md` に1行、回帰2件。骨格には触らない。

## 案2: 語彙の**組み合わせ**を作る

### 何が無いか

`generate_palette.py` は基準色1つから3候補を作る。色以外——版面の motif、文字の扱い、装飾——には語彙が無い。design-principles §5 は「署名を主題から作れ」と要求するが、引き出しが無い。

### 参考にする機構

`sunchaokun/pptx-designer` の `renderer/theme.py` の `ThemeComposer`。**標準ライブラリだけで動く**。

1. クエリ文字列から気分（mood）をキーワード部分一致で検出する
2. 気分ごとの候補プールから、カテゴリ別（palette / fonts / decoration / layout）に1つずつ選ぶ
3. 選択は `random.Random(seed).choice()`。**シードを渡せば再現する**
4. 選んだ生の色を semantic role（background / surface / ink / muted / accent / …）に写像する
5. 候補に無い要求は `fallbacks` に記録して既定に差し替える（監査できる失敗許容）

気分ゲートが効くので、意味的に破綻した組み合わせ（「墨絵」の気分に「ネオンの線」）が出ない。

### この案での形

**色は今のまま**（`generate_palette.py` が主題から導くほうが、既製プールから選ぶより強い）。足すのは**色以外の2カテゴリ**だけにする。

```json
"motifs": {
  "帳簿・台帳": {"mark": "締め線", "geometry": "行の揃った明細", "keywords": ["収支","予算","精算","原価"]},
  "計器": {"mark": "目盛", "geometry": "しきい値のある帯", "keywords": ["監視","閾値","異常","稼働"]},
  "図面": {"mark": "寸法線", "geometry": "寸法の入った断面", "keywords": ["製造","設計","公差","部品"]},
  "被覆": {"mark": "取得点と未取得点", "geometry": "格子の疎密", "keywords": ["網羅","カバレッジ","抜け漏れ"]}
}
```

`palette_basis` の文とブリーフの主題に対してキーワードを部分一致でスコアリングし（siril9 の `_route_score()` と同じ作り。`in` と加点だけ）、**上位3つを候補として出す**。

### 固定デザインにしないための線引き

- **選ばせない。候補を出すだけ。** 採用するには `design-lock.md` に「この主題でこの形が意味を持つ理由」を1行書かせる。書けないなら不採用
- **却下条件を各エントリに持たせる**（`sunchaokun` の `do_not_use_for` に相当）。例: 帳簿は「金額が主題に無いなら使わない」
- **一致が弱いときは何も出さない。** スコアが閾値未満なら「主題から自分で作れ」と返す。無理に当てはめると、まさに「別の主題に移せる署名」になる
- 語彙は**出発点であって既定値ではない**と明記する（既存の言い回しに揃える）

### 見積り

`pptx-design/references/motif-vocabulary.md`（語彙とスコアリングの説明）、`scripts/suggest_motif.py`（標準ライブラリのみ、`--help` と終了コード）、回帰2件（当たるケース／閾値未満で何も出さないケース）。

## 案3: 構成（outline）を機械可読にする

### 何が無いか

`outline.md` は散文で、「主張文タイトル」「証拠と出典」「候補: A / B。選: A。理由: 〜」を書けと指示しているが、**書いたかを誰も確かめていない**。ゲート1は生成物を見る検査で、計画は見ていない。

### 形

`deck/outline.json` を足し、**`outline.md` は捨てない**。`.md` は人が読んで筋を確かめるため（ゴーストデッキテスト）、`.json` は機械が欠落を拾うため。二重に書かせるのではなく、`.json` を正とし `.md` は `.json` から起こす。

```json
{"pages": [
  {"n": 1, "title": "西日本の配送遅延は在庫の偏りが原因である", "role": "主張＋証拠",
   "archetype": "claim-evidence", "exhibit": "chart:bar", "density": "high",
   "evidence": "社内WMS 2026年4-8月の実績",
   "candidates": ["claim-evidence", "comparison"], "chosen_because": "軸が1つで対象が6拠点なので棒"}
]}
```

### 検査（`check_outline.py`、標準ライブラリのみ）

**JSON Schema は使わない**（`jsonschema` は使えるライブラリに無い）。素朴な検査で足りる。

| 見るもの | 落とす条件 |
|---|---|
| 主張文タイトル | 体言止め・話題ラベル（「まとめ」「効果」「概要」など）で終わる。既存の `TITLE_TOPIC_LABEL` の語彙を流用する |
| 決め手 | `candidates` が2つ未満、または `chosen_because` が空 |
| 出典 | 数字を含むページに `evidence` が無い |
| 原型 | `archetype` が骨格の `skeleton()` に無い名前（`audit-consistency.py` と同じ抽出で照合） |
| 密度 | 全ページが同じ `density` |

終了コードは lint に揃える（0=合格 / 1=指摘あり / 2=実行不能）。

### 見積り

`pptx-create/scripts/check_outline.py`、`storyline.md` に節を1つ、`SKILL.md` 工程2に1行、回帰2件。

## 採らないもの

| 案 | 理由 |
|---|---|
| スタイルコーパスの輸入 | 中身が「13分類×固定テンプレート」で、語彙の多様性を提供しない（上の訂正） |
