# 改善案・第2巡 — 和文固有の弱点と、まだ手つかずの領域（2026-09-06）

第1巡（`improvement-plan-2026-09.md`）で6件を入れた後、**他のスキルが扱っていない領域**を探した。結論として、いちばん大きい欠落は比較対象の外にあった——**和文の折り返し**である。

## 入れたもの

### 1. 行数を実際に折り返して数える（`b26e019`）

**三者が食い違っていた。** 描画（`render_preview.py` の `wrap_units`）は1文字ずつ実際に折り返すが、骨格の `wrapped_lines()` と lint の `estimate_overflow()` は「全幅 ÷ 行幅」の切り上げで見積もっていた。

和文は語の途中で折れないので、行末に入りきらなかった分が毎行余る。割り算はその余りを数え落とす。

**実測**: 現実的な和文の文と幅の組み合わせ44通りのうち、**5通りで実際の折り返しが見積りより1行多かった**。1行ずれると下に積んだものと重なる——このセッションで2度直した壊れ方と同じである。

禁則（JIS X 4051）も数える。行頭に置けない文字（`、。）」・？！`、小書きの仮名、長音符など）と行末に置けない文字（`（「『【` など）が来たら、直前の文字ごと次行へ送る（**追い出し**）。

**ぶら下げは当てにしない。** PowerPoint の既定では働かない。追い出しは行が増える側なので、見積りとしても安全側に倒れる。

文字クラスが骨格と lint の二箇所にあるため、整合監査に `check_kinsoku()` を足した。**構文木から定数を読んで照合する**——正規表現だと隣の定数まで拾ってしまい、片方だけずらしたのに両方が違うと報告してしまった。

### 2. 代替テキスト（`cac1420`）

読み上げと、画像が出ない環境で内容が伝わるかを誰も見ていなかった。骨格に `describe()`、lint に `ALT_TEXT_MISSING` と `ALT_TEXT_USELESS`（種類しか言っていない語の denylist）。**種類ではなく中身を言う**を規則にした。

## 調べて分かったこと

- **BudouX は使わない。** Google の語分割器で、目的は「読みやすい位置で折る」であって禁則ではない。Adobe も BudouX の上に**規則ベースの禁則を別途足している**。こちらが要るのは規則ベースの側で、それは標準ライブラリで書ける（文字クラスの表を持つだけ）。ライブラリ依存を増やす理由が無い
- **和文を扱っている比較対象は無かった。** 公式 `pptx` スキルの書体の節も、siril9 も、danny0926 も、扱いは欧文の前提。折り返しの数え方が割り算のままでも欧文では語単位で折れるので誤差が小さく、露見しにくい
- **siril9 の `accessibility_qa.py`** は alt text を汎用語の denylist つきで見る。この観点はそのまま移植価値があった（上の2）

## まだ手つかず

### ~~A. 図の語彙~~ → 1つだけ足し、3つは採らなかった

「内容の形が要求するものだけ」という条件で1件ずつ判定した。

| 候補 | 判定 | 理由 |
|---|---|---|
| **注記（`annotate`）** | **採用** | 図を置いただけでは何を読み取ればよいか分からない。「この3拠点が基準を超える」の一文があるかで、同じ図が主張を運ぶか装飾かが決まる。既存の道具では書けない（`connect()` は図形どうしのみ） |
| 進捗バー・メーター | 不採用 | `rect(下地) + rect(実績)` の2行で書ける。専用部品にすると「達成率でもないのに進捗バーを置く」誘因になる |
| 任意の2点間の矢印 | 不採用 | 欲しくなったら、それは図形どうしの関係なので `connect()` が正しい。自由な矢印は斜めに空間を横切る線を招く |
| サンキー・ネットワーク図 | 不採用 | ネイティブに作れず、画像にすると「ネイティブを守る」に反する。組み直せないなら、そのページに要るのかを疑う（現行の記述のまま） |

`annotate()` は**誤用しにくい形**にした。図の枠と指す点を渡すと、近い辺から順に試して本文領域に収まり図とも重ならない位置を選び、置けなければ例外を出す。最初は `side` を呼び出し側に指定させたが、上に出すとタイトル帯に食い込み、右に出すと図に重なった（どちらも lint が後から拾う形になった）。

**文字は強調色にしない。** 注記の大きさ（12〜14pt）で強調色を使うと、地とのコントラストが本文の下限 4.5:1 を割る——今回入れた `TEXT_CONTRAST_LOW` が最初の実装で実際に拾った。指し示すのは線の仕事にした。

### ~~B. 出力の良し悪しを測っていない~~ → 軽い版を入れた

証拠は全部「lint が通る」である。**素の「パワポ作って」より良いという測定を一度もしていない。** siril9 は盲検3群比較（凍結プロンプト・3シード・失敗も分母に残す）を持つが、評価設計そのものが仕事になる。

`measure-skeleton.py` が同じ内容を骨格版と素の python-pptx 版で組み、比べる。

    指摘の合計          骨格 5 / 素 19
    SHAPE_TEXT_UNSTYLED  骨格 0 / 素 14
    検査できない箱        骨格 0 / 素 14

**素の版の「はみ出し 0」は健全さではない。** `add_textbox` の既定が `spAutoFit` なので、溢れる代わりに箱が下へ伸びて次の要素と重なり、溢れとして計上されない。骨格の効き目は欠陥を減らすことだけでなく、**デッキを検査できる状態に保つこと**にもある——これは測って初めて言えた。

人手の採点は入れていない。盲検の比較は依然として未着手である。

### ~~C. 図表の設計品質~~ → 入れた

`chart()` は書式の最低限を整えるが設計の良し悪しを見ていなかった。4つの検査を足した。

| コード | 重大度 | 見るもの |
|---|---|---|
| `CHART_AXIS_TRUNCATED` | 重要 | 棒の縦軸が0から始まらない（差が実際より大きく見える） |
| `CHART_TOO_MANY_SERIES` | 軽微 | 系列が5本以上（色で追えない） |
| `CHART_PIE_TOO_MANY` | 軽微 | 円が6区分以上（面積を比べられない） |
| `CHART_BARS_UNSORTED` | 軽微 | 単系列の棒が値順でない |

**並べ替えは常に正しいわけではない**（時系列や拠点の順がある）ので、軸の切り詰め以外は軽微に留めた。

### ~~D. 読み上げ順序~~ → 入れた

`READING_ORDER_TITLE_LATE`（タイトルが最初に読み上げられない）と `READING_ORDER_FOOTER_EARLY`（フッターが本文より先）の2つに絞った。「見た目の順序と文書順の一致」を一般に見ると、意図的な脇注や非対称な配置を咎めてしまうため。

## 残っているもの

**盲検の比較**（人が採点する3群比較）だけが未着手である。`measure-skeleton.py` が言えるのは「機械的に検出できる欠陥をどれだけ減らすか」までで、**デッキが良いかどうかは測っていない**。ここを埋めるには評価設計そのものが仕事になるので、今回は範囲外とした。
