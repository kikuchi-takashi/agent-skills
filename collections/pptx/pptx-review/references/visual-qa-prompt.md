# 視覚QA定型プロンプト — バグ狩りとして依頼する

`pptx-create` の `qa.md` のゲート3と、このスキルの手順2〜4は「pptx-review を別コンテキストで走らせることを勧める」ところまでしか書いていない。実際に何を依頼するかは呼び出す側の即興に任されていた。

即興のプロンプトは「確認して」「レビューして」のように**検収の姿勢**で書かれがちである。検収は「無ければ合格」で止まる。実際に直近で見つかった不具合——描画に出た意図しない灰色枠、EXIF回転が反映されず横倒しになった写真、行送りを倍率(`spcPct`)指定したために書体依存で詰まって見える箇所——は、どれも `pptx_lint.py` の41コードのどれにも該当せず、人が画像を実際に開いて「あれ、おかしい」と気づいたことで見つかった。検収の姿勢では、これらは「lintが通っているから良い」で素通りする。

このファイルは、生成・編集を行ったエージェントが**別コンテキストのサブエージェントに視覚QAを依頼するときにそのまま貼る定型プロンプト**を提供する。姿勢を「検収」から「バグ狩り」に変える。

## 使い方

1. 対象デッキで `pptx_lint.py` と `render_preview.py --sheet` を実行し、`qa/lint.json` と `qa/preview-*.png` を作る（`qa.md` ゲート3、`pptx-review` SKILL.md 手順1〜2のとおり）。
2. 下記プロンプトの `{…}` を**絶対パス**に置き換える。相対パスを使わない——サブエージェントは呼び出し元と作業ディレクトリが違うことがあり、解決に失敗する。`{n}` は `render_preview.py` が作った画像の枚数。
3. 得られた文面を、生成・編集を行ったコンテキストとは別のサブエージェントに渡す。同じコンテキストで自分に言い聞かせても、生成時の思い込みは消えない。

## 定型プロンプト

```
あなたはこれから {file} の見た目を確認する。ただし「確認して」「問題ないか見て」という
検収の依頼ではない。バグ狩りとして依頼する。次を前提にする。

- 最初のレンダリングは、ほぼ確実にどこかが正しくない。「特に問題ありません」は結論ではなく、
  まだ十分に探していないことの兆候として扱う。
- あなたはこのデッキを作っていない。生成した本人は頭の中でレイアウトを補完して見てしまうが、
  あなたはそれをしない。画像に実際に写っているものだけを事実として扱う。
- 機械検査（lint）が拾わない不具合がある。過去に人が画像を見て気づき、機械検査がゼロ件だった
  実例: 意図しない灰色の枠線が描画に出ている、写真がEXIF情報どおりに回転されず横倒し・天地
  逆になっている、行送りが詰まりすぎ／間延びして見える（倍率指定は書体依存で高さが変わる）。
  これらと同じ種類の「lintのコードには無いが目には見える」ものを探す。
- 手組みに見える不揃い（署名、非対称なレイアウト、意図的なずれ）は減点しない。咎めるのは、
  意図が読み取れない不揃いと、明白な欠陥（はみ出し、重なり、切れ、崩れ）だけである。
  「テンプレートのように均質でない」ことを「粗い」と誤認しない。

## 確認する物
- lint結果（JSON）: {lint_json}
- ページ画像（全{n}枚）: {preview_glob}
- 一覧画像: {sheet_png}
- デザインロック（あれば）: {design_lock}
- 構成（あれば）: {outline}

## 手順
1. lint結果の errors と warnings を先に読み、コードと該当ページ・図形名を頭に入れる。
2. ページ画像を1枚ずつ開く。一覧画像だけで済ませない。見る順序は review-rubric.md の
   「目視の順序と観点」（はみ出し→重なり→余白→整列→コントラスト→視覚の兆候→文章の兆候→
   主張と展示物→編集可能性）に従う。
3. 上記の実例と同じ種類の、lintのコードに無い症状を重点的に探す。特に:
   - 意図しない線・枠・影が描画に出ていないか（コードが消したはずの枠が残っていないか）
   - 画像の向き・天地・トリミングが不自然でないか
   - 行間・字間が詰まりすぎ／空きすぎに見えないか
   - 書体の代替により、想定と違う太さ・幅・和文/欧文の混在が起きていないか
   - 色が、数値上のコントラスト比以上に画像として見ると弱く・強く見えないか
4. 1周目で「問題ない」と判定したページだけを、もう一度見る。1周目の思い込みを疑う2周目を
   省略しない。
5. 指摘は「ページ番号・図形名・症状・見えた場所・確信度（確実／要確認）」で書く。確信が
   持てない微妙な指摘も、要確認として残す。握りつぶさない。

## 報告する形式
- 見たページ数（全ページを見たことを明記）と、周回数
- 指摘の一覧。0件なら、何を何回見てゼロだったかという根拠を添える。根拠の無いゼロ件報告は
  「合格」ではなく「未実施」として扱う
- lintに無い症状を探した結果（見つからなければ「探したが無かった」と書く。これは「見て
  いない」とは違う）
- 見ていないもの・確認できなかったもの（書体が代替されている、画像形式が読めない、など）
```

## この姿勢が既存の原則と矛盾しない理由

`review-rubric.md` の4b「設計の判定」は、署名・形式の選択・主役の3項目に限って「手組みに見えるから」を理由に減点しないと定める。これは**主題から作られた不揃いを守るための例外**であり、「不揃い全般を疑わない」という意味ではない。上のプロンプトも同じ境界線を引いている。

- 咎めない: 全ページ同じテンプレートで量産したように見えないこと自体（署名・形式・主役の不揃い）
- 咎める: 意図の読み取れない崩れ（枠線のバグ、写真の天地、行送りの詰まり）

「バグ狩りとして臨む」は後者を指す。前者を疑えという意味ではない。プロンプト本文にもこの区別を明記し、「テンプレートのように均質でないことを粗いと誤認しない」と書いた。

## 機械に落とせた分と、落とせない分

視覚QAが毎回同じことを人手で探すのは非効率なので、機械的に判定できるものは lint に移した。

- `TEXT_CONTRAST_LOW`（文字と地のコントラスト）— 追加済み。地が画像・グラデーション・半透明・未解決の色のときは**咎めず**、`measurement.contrast_unmeasured` に数える
- 描画そのものの退行（消したはずの枠が出る、面が塗られない）— `scripts/visual-baseline.py` が図形だけの見本の画素を基準と突き合わせる。文字のある画は書体で変わるので基準にできない

落とせないものは残る。**写真の天地・トリミングの不自然さ、書体代替による見え方、半透明の面越しの読みやすさ**は、画素を人が見るしかない。上のプロンプトはそこに使う。
